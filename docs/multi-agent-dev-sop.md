# 多 Agent 协作开发 SOP

三角色协作：**架构-agent →（后端-agent ∥ 前端-agent）→ 集成与浏览器自动化测试**。角色定义见 `.claude/agents/`（主控在任何会话中用 Agent 工具按名调用）。

**日常开发入口（自定义命令，`.claude/commands/`）**：`/dev-backend <需求>` 纯后端轨道 · `/dev-frontend <需求>` 纯前端轨道 · `/dev-fullstack <需求>` 全栈轨道 · `/dev-regression` 起全栈跑 e2e 回归。命令是薄编排层（本 SOP 的阶段清单化），流程细节仍以本文档为唯一来源。

## 需求轨道（按改动面组装；superpowers 全轨道强制——任何轨道 spec/plan 先行，不得因单端需求跳过）

| 轨道 | 判定 | 阶段组装 | 验收终点 |
|---|---|---|---|
| 全栈 | 前后端都动（新功能/契约新增） | 架构 → 后端∥前端 → 集成 → 浏览器测试 | 浏览器自动化 + 视觉核对 |
| 纯后端 | 仅 cloud-base 动 | A 级走架构 / B 级主控直带 → backend-agent | 单测+守护测试 → curl 逐条；**无 UI 不做浏览器测试** |
| 纯前端 | 仅 cloud-web 动 | A 级走架构 / B 级主控直带 → frontend-agent | build+代理联通 → 浏览器测试（cloud-e2e 增/改场景） |

**架构介入分级**：

- **A 级（必须架构-agent）**：新接口/新表/契约变更/跨服务/技术选型/UI 架构级改动 → 输出三文档，**只写涉及端的章节与任务清单**（纯后端需求无前端章）。
- **B 级（主控直接带实现 agent）**：bug 修复/样式与交互微调/文案/既有契约内的参数补全 → 无 contracts，但 superpowers 轻量 plan 仍必须（一份 plans 文档含验证标准）。
- **C 级（模板化增量，主控直接做）**：照着既有模板新增、不引入新行为。同时满足以下四条才算 C 级：
  1. 有一份现成实现可逐字照抄结构（如：给已有「实体+DAO」模式再加一张表的实体与 DAO）；
  2. 零契约变更（不新增/修改任何对外接口）；
  3. 零新增错误码、零新增权限标识；
  4. 改动面 ≤ 6 个文件。

  C 级**不写 plan 文档**：测试先行，commit message 按「改动点/验证/欠账」三段写清即可（见下文可读性标准）。做到一半发现不满足任一条 → 立即升 B 级补轻量 plan。
- **升级红线**：凡改动会变 API 行为/表结构/共享配置 → 一律升 A 级（B 级判定存疑时按 A 级走）。注意：C 级里「新增一张表的实体与 DAO」指**表已由 A/B 级轮次定稿**，建新表本身仍属 A 级。

**跨轨道规则（契约变更的前端影响面）**：纯后端需求若修改**既有契约**，前端虽不开发但受影响——主控必须跑 `cloud-e2e` 全量回归（`cd cloud-e2e && npm run e2e`）确认既有页面不破；回归红了才拉 frontend-agent 进场跟进。

## 流程总览（全栈轨道完整形态；单端轨道按上表裁剪）

```
用户需求
   │
   ▼
①架构-agent（superpowers: brainstorming → writing-plans）
   阶段一 需求分析与讨论：回报《需求分析》（领域理解/边界/关键问题与候选方向/范围建议），不出方案
   │  └─ 主控提炼要点呈用户讨论，关键分歧 AskUserQuestion 拍板；结论经 SendMessage 带回同一架构实例续跑
   阶段二 方案设计（输入 = 分析 + 拍板结论）：输出三文档：技术方案 specs/ + API 契约 contracts/ + 实施计划 plans/（后端/前端任务两章，标注并行）
   │
   ├── 主控对方案做规格审查（可轻审：契约完整性/规范一致性）
   │
   ▼
②并行派发（两个 Agent 工具调用放同一条消息 = 真并行；不同目录零冲突）
   ├── backend-agent：按契约+计划实现 → 守护测试全绿 → curl 验收
   └── frontend-agent：按契约实现（后端未就绪先 mock）→ build+dev 联通
   │
   ▼
③集成（前端-agent）：dev proxy 指向网关 18080，起全栈（应用服务 agent 自主接管，见「服务进程管理」）
   │
   ▼
④浏览器自动化测试（前端-agent；需 Playwright MCP）
   导航/表单/断言 + 截图 → analyze_image 视觉模型核对 UI
   │  └─ 联调+冒烟（含 e2e 回归）全部通过 → 关闭 agent 起的全部服务进程（见「服务进程管理」）
   ▼
⑤双审（spec 审查按契约逐条 + quality 审查）→ 修复循环 → 合并 main（人工审核期间用户自起服务查看效果）
```

## 关键规则

1. **契约先行**：API 契约（`docs/superpowers/contracts/`）是前后端唯一对齐物，架构 agent 定稿后**两端都不得单方修改**；变更须回架构 agent 出契约修订。
2. **并行不阻塞**：前端拿契约即可开工（mock 模式），后端实现有守护测试保契约稳定；集成阶段切换真实联调。
3. **主控（会话本身）职责**：拆解派发、架构阶段一的讨论中转（提炼《需求分析》要点呈用户，拍板结论带回同一架构实例——子代理不直接面对用户）、给子代理完整任务上下文（贴契约/计划全文，不让其自读零散文件）、处理 NEEDS_CONTEXT 上报、跑两阶段审查、git 操作与合并。
4. **模型分配**：架构/后端/前端实现继承会话模型；截图视觉核对/简单冒烟可由主控在派发时指定轻量档。具体型号不写进本文档（会随版本变）。
5. **测试金字塔（按轨道取顶）**：后端单测+守护测试（构建期）→ 外部依赖冒烟（见下）→ 接口 curl（后端验收）→ 浏览器自动化+视觉核对（**有 UI 改动轨道**的集成验收；纯后端轨道止于 curl）。
6. **外部依赖冒烟（接入新外部系统必做）**：单测用内存替身（如 SQLite）覆盖不到真实系统的类型与方言差异——例如 Milvus 主键类型由 `auto_id` 决定、MySQL 连接串的字符编码。每接入一个外部系统（数据库、向量库、模型服务、消息队列），必须附一个**可单独运行的真连接冒烟脚本**，放 `cloud-base-ai/scripts/smoke/`，验收时真跑一次并把输出写进报告。脚本不进单测套件（单测不得依赖外部服务）。

## 提交署名

提交信息与 PR 描述的署名行**以当前会话的署名指令为准**，不在本文档、agent 定义、命令文件里写死具体模型名。会话没有给出署名指令时，主控向用户确认，不自行杜撰。

## 验收挂起规则（基础设施不可用时）

背景：验收依赖 MySQL、Nacos、Redis、Milvus 等本机基础设施，它们可能没起。此前遇到这种情况，轮次会带着未验证的项直接提交，欠账随后淡出视线。

**允许挂起的项**：只限因基础设施不可用而无法执行的**运行时验收**（真库落库、curl 实证、e2e 回归）。单测、守护测试、构建**不允许挂起**，必须全绿。

**挂起时必须做**：
1. 在 `docs/handoff/<域>.md` 登记一条欠账，写明：缺什么基础设施、待执行的具体命令、预期结果；
2. 在提交信息的「欠账」段引用这条记录；
3. 向用户明示：本轮「代码已完成、运行时未验证」。

**清账纪律**：同域下一轮开工前，**先清欠账再开新功能**。清账后删除 handoff 里对应条目（只留未兑现的，已兑现的不留痕迹）。

`docs/handoff/<域>.md` 的格式：一个条目一个二级标题，条目内只有「待办 / 命令 / 预期 / 登记日期」四项。这个文件只放**当前仍欠着**的事，不是历史记录。

## 文档体量约束

背景：目前 plans 目录共 39 份文档，其中最长的一份 3236 行，为只有两张表的 DAO 轮写的计划也有 1539 行。过长的文档没人读，与可读性标准的目的相冲突。

| 文档 | 体量上限 | 写法要求 |
|---|---|---|
| C 级 | 无文档 | 见「C 级」，信息全部进 commit message |
| B 级 plan | 约 150 行 | 每个任务只写：文件清单、验收标准、关键约束。**不贴完整实现代码** |
| A 级 plan | 约 400 行 | 同上；超出时拆成多份按子系统分的 plan |
| spec | 约 300 行 | 只写取舍与结论，不写实现细节 |

**不贴完整代码的理由**：实现 agent 本来就会写代码，plan 里再贴一遍既占篇幅，又会在实现时和真实代码产生分歧。需要贴的只有两类：①接口签名与数据结构（契约性的）；②容易写错的关键片段（≤15 行，并说明为什么容易错）。

超限不是硬错误，但双审阶段按「可读性」项扣分；超过上限 1.5 倍必须拆分。

## 文档与注释可读性标准（全角色产出强制，2026-10-14 定版）

适用面：specs/contracts/plans 三文档、代码注释、commit message、实施报告与简报——**含主控自己的产出**。统一写给「第一次接触本项目的人」：他没读过上一轮的方案，看不懂内部编号。

### 代码注释

1. 注释只回答两个问题：**这段代码做什么、为什么这么做**。方案对比、轮次历史、拍板过程不进代码，落 specs/plans 文档。
2. **决策代号禁止裸引用**：`D1`、`T5`、`B7`、`方案B`、`spec §3` 这类编号离开定义它的文档就是天书。要么展开成一句话，要么写「一句话结论 + 文档路径」。
3. 一行注释只说一件事；句子宁短勿长，括号嵌套最多一层；术语第一次出现给一句话解释（如 TOCTOU → 并发下的查重窗口）。

反例（本仓库真实产出，勿效仿）：

```python
"""router 端点断言（B7 / spec D5/D6/D12 + 契约 §2/§3）：TestClient 全 mock 零网络。"""
```

正例：

```python
"""router 端点测试：TestClient 全 mock，不发真实网络请求。

异常分支与 SSE 帧协议的设计取舍见
docs/superpowers/specs/2026-10-13-ai-rag-chat-design.md。
"""
```

### 文档与报告

1. **结构化优先**：小标题 + 列表/表格；一段只说一个主题，长句拆短句。
2. **结论先行**：每节第一句是结论，理由和过程跟在后面。
3. 决策记录三行式：背景一句话 → 候选与取舍 → 结论。不写意识流。
4. 代号（D1/T5/方案B 等）只允许在**定义它的那份文档**内使用；跨文档引用必须写明出处。
5. commit message：首行一句话说清做了什么；正文按「改动点/验证/欠账」分短段，禁止巨型单段。

### 自检与把关

交付前通读一遍产出，只问一个问题：**不懂项目历史的同事不查其他文件能否读懂？** 答不上来就重写。双审阶段主控按本标准专项检查——发现裸代号、无结构长段、未解释术语即打回修复。

## 服务进程管理（2026-10-09 定版；应用服务全生命周期归 agent）

- **开发过程中**：agent 自主接管**全部应用服务**并自行启停，无需逐步请示、卡点不等人手动重启——后端 9201/9202/9203/18080（`java -jar` 绝对路径后台运行；业务服务先起、网关 18080 最后）与前端 dev 5173。
- **关闭时点**：待前后端功能联调测试并通过冒烟测试（本轨道自动化验证整体收口——触及契约/有 UI 时含 e2e 全量回归）后，**立即 kill 本轮 agent 起的全部服务进程**（`netstat -ano` 找 PID + `taskkill //F //PID`）。服务不滞留进入双审/人工审核阶段——避免 agent 遗留进程占用端口与内存、影响人工开发审核；人工审核期间用户需要看效果自行起服。
- **复验回路**：双审或回归发现问题需再验证时，agent 再次接管起服，验证通过后再次关闭（同一收口纪律）。
- **边界**：仅应用服务。Nacos/Redis/MySQL（Docker/原生基础设施）永不触碰；用户自己起的进程（如 IDEA Run）不动，除非用户要求。

## Playwright MCP 安装（一次性，用户终端执行）

```
claude mcp add playwright -- npx @playwright/mcp@latest
```

装好后重启 Claude Code 会话；未装期间前端-agent 按其定义走降级验证（build+curl+webReader）。
